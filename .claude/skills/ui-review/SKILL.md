# ui-review

画面を、作った文脈を知らない目で見直す手順。返ってくる指摘は**仮説**で、検査ではない。そのため `make check` と CI には入れない。決定的に確かめられること（横にスクロールしない、axe の違反がない、通しのシナリオ）は、今どおり `frontend/e2e/` の検査に書く（ADR-0017）。

## いつ使うか

- 画面の構成・配置・状態の見せ方（待っているあいだ、選んだ枠、鳴っている枠、失敗）を変える PR を出す前。
- 配置の案を見比べるとき。案ごとに撮り、同じ手順でレビューさせる。
- 文言だけの変更には使わない。

## 手順

1. **動かす。** `make e2e` と同じ仕組みで動く。先に API をビルドする（`make backend-build`）。Chromium が要る。取り方と `PW_CHROMIUM_PATH` は `docs/dev/harness.md` の「画面（実ブラウザ。ADR-0017）」の節。API と画面の開発サーバーは、Playwright の `webServer` が専用のポート（`frontend/playwright.config.ts`）で起動して止める。`make e2e` と同時には走らせない（ポートがぶつかる）。
2. **撮る。** `cd frontend && npm run ui:shots`。
   - 状態ごと（`1-first` 最初の画面、`2-added` 和音を足した、`3-chosen` 計画のタブで枠を選んで候補と変形が出た、`4-explored` 5 枠の進行で探索のタブのノードを選んだ）に、幅 360・768・1280（高さ 800、配置の検査と同じ）で撮る。
   - `frontend/ui-review-out/` に、`<状態>-<幅>.png`（ページ全体）と `<状態>-<幅>.aria.yaml`（Playwright の `ariaSnapshot` で取ったアクセシビリティツリー）を書く。出力先は `UI_SHOTS_DIR` で変えられる。
   - 撮る状態を足すときは、`frontend/e2e/ui-shots.ts` の `states` に足す。
   - 撮ったら、画像を 1 枚開いて、画面が写っているか（待っている途中や、失敗の画面でないか）を自分で確かめる。
3. **約束を集める。** 画面の約束は `docs/product/screen-promise.md`（目標の画面。ADR-0019）。次を約束として写す。
   - 目標の画面を変える PR: 約束の文書の 1（満たす体験 E1〜E5）と、対象の区画の約束。暫定で動いているところ（約束の文書の 5）と、まだ決まっていないこと（6）も添える。
   - 今の画面を変える PR: 今の画面は目標の骨組み（約束の文書の 2）までを満たす。約束の文書の 1 と 2、`docs/architecture/screen.md` の「配置」と、対象の状態に関わる節（「候補」「枠を埋める候補」「変形」「役割」「鳴らし方」「読みの失敗」から選ぶ）を約束にする。
   - PR の意図（何を変え、何を確かめたいか）を 1〜3 行で添える。
4. **レビューさせる。** 文脈を共有しないサブエージェント（Agent ツールの `general-purpose`）を 1 つ起動する。渡すのは次のものだけにし、自分の見立ては渡さない。
   - 画像と `.aria.yaml` のパス。全部でなくてよい。見比べたい状態と幅に絞る。
   - 3 の約束と意図。
   - HCI の知見の索引（`.claude/skills/hci/index.md`）。根拠を索引の項目名で示させる。
   - 依頼文は下の例を使う。
5. **確かめる。** 返ってきた指摘を 1 件ずつ、コード・画面・約束に当たって、次の 3 つに分ける。
   - 裏が取れたもの
   - 誤読（画像の読み違い、約束にない前提、画像から読めない動きや音を事実として書いたもの）
   - 判断が要るもの

### 依頼文の例

> あなたは chord-rambler の画面を初めて見るレビュアーです。chord-rambler は、ユーザーがコード進行を自分で選んで組み上げ、鳴らしながら学ぶ作曲支援アプリです。
> 添付の画面の画像と、アクセシビリティツリー（`.aria.yaml`）を、下の画面の約束と意図に照らしてレビューしてください。ファイルは Read ツールで開けます。
> 主な作業（〈例: 和音名で C を足し、末尾に足す候補を見比べて 1 つ足す〉）の 1 歩ごとに、次を問うてください。その状態で、次に何をすればよいか分かるか。そのための操作が見つかるか。操作のあとに、何が起きたか分かるか。画像とツリーで、名前や並びが食い違っていないか。
> 指摘は「どこで（状態・幅・場所）／種類（約束とのずれ、分かりにくさ、配置、アクセシビリティ）／重大度（高・中・低）／確信度（高・中・低）／改善案と確かめ方」の表で、重大度の高い順に最大 10 件返してください。画像から読めないこと（動き、音、時間の経過）は推定と明記してください。良い点も 3 件まで挙げてください。
> 〈画面の約束と意図をここに貼る〉

## 指摘の扱い

- 誤読は捨てる。
- 裏が取れたものだけを PR に書く。書く場所は「レビューの見どころ」。何を読んで裏を取ったかを添える。
- 判断が要るもの、今の PR の範囲の外のものは、PR で直さず、`observation` の Issue にする（`docs/dev/workflow.md` の「Issue の使い方」）。
- 決定的に確かめられる指摘（要素が幅に収まらない、名前がない）は、直すと同時に `frontend/e2e/` の検査に足すかを考える。
