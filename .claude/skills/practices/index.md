### テストの大きさを制約で決め、小さいものを既定にする

| 欄 | 内容 |

| 出どころ | Adam Bender「Testing Overview」（Software Engineering at Google 11 章）。https://abseil.io/resources/swe-book/html/ch11.html |
| ソース | `abseil/abseil.github.io:resources/swe-book/html/ch11.html@e9e2483` |
| 何を言っているか | テストを「どれだけのコードを確かめるか（範囲）」とは別に、「どう走るか（大きさ）」で分ける。最小の大きさは、単一のプロセスの中で、待ち・入出力・ネットワークを使わないもの。速さと決定性はこの制約から得られるので、できる限り小さい大きさで書く。どの大きさでも、実行の順や共有の環境に依らず、自分で準備と後始末をする。 |

## 4. 変更の分け方とレビュー

### 小さな変更にし、構造と振る舞いを分ける

| 欄 | 内容 |

| 出どころ | Google Engineering Practices「Small CLs」。https://google.github.io/eng-practices/review/developer/small-cls.html 。Martin Fowler「Workflows of Refactoring」。https://martinfowler.com/articles/workflowsOfRefactoring/ |
| ソース | `google/eng-practices:review/developer/small-cls.md@3bb3ec2` |
| 何を言っているか | 変更は自己完結した 1 つのことに絞り、関連するテストを同じ変更に入れる。大きさは行数だけでなく、散らばるファイルの数でも決まる。リファクタリングは、機能の追加やバグの修正と別の変更にする。Fowler は、振る舞いを保つ変更（テストは通ったまま）と、機能を足す変更を同時にしないと言う。 |
| 確からしさ | 公式の推奨（Google）と、広く共有された実務の知見（Fowler）。大きさに固定の規則はなく、小さすぎて意味が読めない変更もよくない（新しい関数は、使う箇所と一緒に出す）。局所的な名前の直しは同居してよい。誤用: 行数だけで機械的に割り、単独では意味の分からない変更を出す。 |
