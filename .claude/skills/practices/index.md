### テストに求める性質は釣り合いで決める

### 振る舞いを公開の入口から、状態で確かめる

| 欄 | 内容 |
| --- | --- |
| 出どころ | Erik Kuefler「Unit Testing」（Software Engineering at Google 12 章）。https://abseil.io/resources/swe-book/html/ch12.html |
| ソース | `abseil/abseil.github.io:resources/swe-book/html/ch12.html@e9e2483` |
| 何を言っているか | 理想のテストは、要求が変わらない限り書き換えずに済む。リファクタ・機能追加・バグ修正では既存のテストは変わらず、変わるのは振る舞いを変えたときだけ。そのために、利用者と同じ入口から呼び、どう呼んだかではなく結果の状態を確かめ、メソッドごとではなく振る舞い（前提・操作・結果）ごとに 1 件書く。 |
| 確からしさ | 広く共有された実務の知見（Google の社内実践の記述）。公開の入口の範囲は単位の切り方しだいで、言語の可視性とは一致しないと断っている。誤用: 補助的な内部関数を直接テストするために可視性を外す。 |
| 当たるべき場面 | 移調・構成音・調の判定など、エンジンの関数のテストを書く、レビューするとき。内部の表現やカタログの持ち方を変えるリファクタで、既存のテストが落ちたとき。 |
| 判断の問い | この差分は振る舞いを変えていないのに、既存のテストを書き換えていないか。テスト名はメソッド名ではなく「どの状況で何が起きるか」を言っているか。 |

### テストは読んで正しいと分かるように書く

| 欄 | 内容 |
| --- | --- |
| 出どころ | Erik Kuefler「Unit Testing」（Software Engineering at Google 12 章）。https://abseil.io/resources/swe-book/html/ch12.html |
| ソース | `abseil/abseil.github.io:resources/swe-book/html/ch12.html@e9e2483` |
| 何を言っているか | テストにはテストがないので、見ただけで正しいと分かることを優先する。本体には結果に至るのに必要な情報をすべて置き、関係のない情報は置かない。期待値は連結・ループ・条件分岐で組み立てず、そのまま書く。重複を減らすことより、読んで意味が分かることを選ぶ。 |
| 確からしさ | 広く共有された実務の知見。重複を許すのは重複を減らす原則の置き換えではなく補いだと断り、無関係な詳細を隠す生成の補助や、1 つの事実だけを確かめる検証の補助は認めている。誤用: 「重複してよい」と読んで無関係な準備まで各テストに写し、何を確かめているかを見えなくする。 |
| 当たるべき場面 | 和音や音階の期待値を書くとき。共有の定数・準備・検証の補助を足すとき。 |
| 判断の問い | 期待値は、本体と同じ計算をなぞって作っていないか（そのまま書けるか）。このテストを理解するのに、テスト本体の外を何か所読む必要があるか。 |

### 依存は本物を優先し、代役は fake、stub、呼び出しの検証の順に選ぶ

| 欄 | 内容 |
| --- | --- |
| 出どころ | Andrew Trenk, Dillon Bly「Test Doubles」（Software Engineering at Google 13 章）。https://abseil.io/resources/swe-book/html/ch13.html |
| ソース | `abseil/abseil.github.io:resources/swe-book/html/ch13.html@e9e2483` |
| 何を言っているか | 依存先が速く、決定的で、組み立てが簡単なら、本番と同じ実装を使う。使えないときは契約に忠実な軽い実装（fake）を第一に選び、fake も本物と同じ契約のテストで確かめる。戻り値の固定（stub）は、対象をある状態に置くための少数に限る。呼び出しの検証は、状態で確かめられないときか、回数や順序そのものが振る舞いのときに、副作用のある呼び出しだけに行う。 |
| 確からしさ | 一流派の主張。mock を主に使う流派があることを認めたうえで、保守の手間のわりにバグを見つけなかった経験から本物を優先すると述べ、釣り合いの問題だと断っている。誤用: 「mock 禁止」と読んで、外部サービスや時計のような非決定的な依存まで本物でつなぐ。 |
| 当たるべき場面 | UI や上の層のテストでエンジンを差し替えたくなったとき（純粋で決定的なので本物が使える）。音の出力・時計・乱数・保存先を扱うテストの設計。mock 用の依存を足すか決めるとき。 |
| 判断の問い | 差し替える依存は、遅い・非決定的・組み立てが重い、のどれに当たるか。検証している呼び出しは、外に副作用を残すものか（戻り値を使うだけの呼び出しを検証していないか）。 |

### テストの大きさを制約で決め、小さいものを既定にする

| 欄 | 内容 |
| --- | --- |
| 出どころ | Adam Bender「Testing Overview」（Software Engineering at Google 11 章）。https://abseil.io/resources/swe-book/html/ch11.html |
| ソース | `abseil/abseil.github.io:resources/swe-book/html/ch11.html@e9e2483` |
| 何を言っているか | テストを「どれだけのコードを確かめるか（範囲）」とは別に、「どう走るか（大きさ）」で分ける。最小の大きさは、単一のプロセスの中で、待ち・入出力・ネットワークを使わないもの。速さと決定性はこの制約から得られるので、できる限り小さい大きさで書く。どの大きさでも、実行の順や共有の環境に依らず、自分で準備と後始末をする。 |
| 確からしさ | 広く共有された実務の知見（Google の社内の分類）。範囲ごとの比率は目安でチームごとに違ってよいこと、範囲が狭くても小さくできない場合があることを断っている。誤用: 範囲が狭いというだけで、入出力や待ちを含むテストを速い層に混ぜる。 |
| 当たるべき場面 | テストの層と、`make check` に入れる範囲を決めるとき。エンジンのテストがファイル・時計・乱数に触れそうなとき。UI のテストにブラウザを使うか決めるとき。 |
| 判断の問い | このテストは単一のプロセスの中で、待ち・ディスク・ネットワークなしに走るか（走らないなら、何がそれを求めているか）。ほかのテストの実行の順や、残した状態に依っていないか。 |

| 対象 | なし |

### 事例をデータの表にする

| 欄 | 内容 |

| ソース | `golang/wiki:TableDrivenTests.md@fe2268b` |

| 確からしさ | 広く共有された実務の知見。出どころは Go の書き方が前提で、ほかの言語ではパラメータ化したテストに読み替える。誤用: 手順の違う事例まで 1 つの表に入れ、行に分岐用の欄を足す。 |

### 例ではなく性質で試す

| 欄 | 内容 |
| --- | --- |
| 出どころ | fast-check の文書「What is Property-Based Testing?」「Why Property-Based Testing?」。https://fast-check.dev/docs/introduction/why-property-based/ 。Hypothesis の文書と、D. R. MacIver「The Encode/Decode invariant」 |
| ソース | `dubzzz/fast-check:website/docs/introduction/what-is-property-based-testing.md@0d28f7b`, `dubzzz/fast-check:website/docs/introduction/why-property-based.md@0d28f7b`, `HypothesisWorks/hypothesis:website/content/2016-04-16-encode-decode-invariant.md@9ab0be6` |
| 何を言っているか | 入力と出力の組を個別に書く代わりに、すべての入力で成り立つべき関係を書き、道具に多数の入力を作らせて反例を探す。反例は小さく縮めて示される。見つけやすい性質は、往復（変換して戻すと元に戻る）、単純で明らかに正しい実装との一致、保存される量、落ちないこと。種を固定すれば再現できる。 |
| 確からしさ | 公式の推奨（各ライブラリの公式の文書）。例によるテストの置き換えではなく追加だと明言している。全部の入力は試せないので、通っても証明ではない。誤用: 遅さや失敗を避けるために入力の範囲を狭め、反例の出る値を締め出す。 |
| 当たるべき場面 | 移調して逆に移調すると戻る、表記の文字列化と解析の往復、転回しても構成音の集合が変わらない、のような不変量を持つエンジンの関数。同じ形の事例の表が長くなったとき。道具の依存を足すか決めるとき。 |
| 判断の問い | この関数に、すべての入力で成り立つと言い切れる関係を 1 つ書けるか（書けないなら例で足りる）。生成する入力の範囲は、関数が受け付けると約束した範囲と同じか。 |
