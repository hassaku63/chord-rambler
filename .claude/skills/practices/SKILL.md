# practices

`index.md` は、設計・実装・レビューのときに当たるべき開発の知見の索引である。決定の理由は ADR-0007。

## 規則は 3 段で持つ

| 段 | 置き場所 | 中身 |
| --- | --- | --- |
| 機械の検査 | `make check`（`docs/dev/harness.md`） | lint・型・テストで強制できること |
| 規約 | `AGENTS.md`、`docs/` の文書、ADR | このプロジェクトが決めたこと |
| 索引 | `index.md` | 決める前に当たる知見 |

上の段に上げられるものは上げる。項目が lint やテストで強制できるようになったら、索引から消す。プロジェクトの立場が決まったら、規約を正とし、項目の「このプロジェクトの立場」からそこを指す。

## 使い方

1. 決めようとしていることを 1 行で言う（例: 「この関数の重複をまとめるか」「この依存をテストで偽物に置き換えるか」）。
2. `index.md` の節の見出しから当たりをつけ、各項目の「当たるべき場面」で絞る。
3. 「判断の問い」を自分の案に当て、当たった項目の名前を PR の「当たった索引の項目」に書く。
4. 細部（数値、API の名前、手順）を根拠に使うときは、出どころを開いてから使う。索引は要点しか持たない。
5. 見直しの期限（確認日 + 間隔）を過ぎた項目を根拠に使うときは、先に出どころを開き直す。開けなければ、開けなかったことを PR に書く。確かめ直す手順は `docs/dev/knowledge-review.md`。
6. 見つからなければ、そう書いて進める。足すべき知見だと思ったら、観察の Issue にする（今の作業に混ぜない）。

## 載せるもの・載せないもの

載せるのは次の 4 種類。学習済みの一般的な知識で足りるものは載せない。

1. 版で変わるもの（採用したライブラリの、今の版での推奨）
2. 流儀が割れるもの（並び立つ立場と出どころ）
3. やりがちな逆（知っていても起きる乱雑さの元）
4. レビューの観点（機械で検出できず、レビューで見るもの）

- 書かない: 出どころの文章の写し、例のコード、手順。出どころを開かずに書いた中身。
- 項目は 40 個まで。超えるなら、足す前に削る。
- 検討して載せなかった知見は、「外したもの」の節に理由と一緒に 1 行残す。

## 項目の形

項目は `###` の見出しと、次の欄を持つ表。`scripts/check-practices.sh` が欄と書き方を検査する。

| 欄 | 書き方 |
| --- | --- |
| 出どころ | 著者と題、URL |
| ソース | Git で公開されていれば `` `owner/repo:path@コミット` ``。なければ「なし」 |
| 何を言っているか | 自分の言葉で 2〜4 行 |
| 確からしさ | 公式の推奨／広く共有された実務の知見／一流派の主張、とよくある誤用 |
| 当たるべき場面 | どの判断のときに引くか |
| 判断の問い | 差分か設計を見て答えられる問い |
| このプロジェクトの立場 | 決めていれば、規約・ADR・検査への参照。なければ「未定」 |
| 対象 | 関係する依存を `` `名前@大きな版` `` で。技術によらなければ「なし」 |
| 確認 | `YYYY-MM-DD / 間隔 N 日`。出どころを実際に開いた日と、見直しの間隔 |
