# grill

所有者の判断が要る問いを出し、答えを Issue に残すまでを行う。決めるのは所有者で、エージェントは問いを整え、事実を調べ、答えを記録する。

対象: $ARGUMENTS

## 手順

1. **対象を決める。** 上の「対象」に Issue の番号があれば、その Issue。なければ、開いている `needs-decision` の Issue を、番号の小さい順に全部。1 つもなければ、「判断待ちの Issue はない」と答えて終わる。
2. **読む。** 対象の Issue の本文とコメントを全部読む。問いに答えるのに要る事実（コード、文書、ADR、外の一次情報）は、自分で調べる。事実を所有者に尋ねない。調べて分かったことで企画の前提が崩れていたら、問いを出す前にそれを伝える。
3. **問いを出す。** 「決めてほしいこと」のうち、前提がすべて決まっている問いを全部、一度に出す。
   - 問いごとに選択肢を並べ、それぞれの利点と欠点を 1 文で書く。推奨を先頭に置き、推奨であることを示す。
   - 問いは、それだけで読めるように書く。Issue の番号と、何についての問いかを含める。
   - 質問のツール（AskUserQuestion）が使えるなら使う。使えなければ、番号つきの一覧で出し、答えを待つ。
4. **繰り返す。** 答えで前提が決まった問いがあれば、3 に戻る。
5. **記録する。** Issue ごとに、答えをコメントに「所有者の判断（セッションでの回答を記録）」として書く。推奨と違う答えと、判断のときに企画を直した点も書く。本文を現在の状態に直し、`needs-decision` を外す。
6. **`ready` の Issue にする。** 決まったスライスは、`docs/dev/workflow.md` の「`ready` の Issue に書くこと」の書式で、`ready` の Issue にする。同じ節の「`ready` にしない」条件に当たるものは、しない。企画の本文のスライスの表に、作った Issue の番号を書く。
7. **終わる。** 記録した判断と、作った Issue の一覧を示して終わる。実装は始めない。

## 守ること

- 所有者の代わりに答えを決めない。推奨は示すが、選ぶのは所有者。
- 答えが出なかった問いは、`needs-decision` のまま残し、残ったことを伝える。
- 所有者にしか決められない問いだけを出す。事実で決まることや、文書や ADR ですでに決まっていることは、問いにしない。

## 出どころ

問いの出し方（前提の決まった問いを一度に、推奨つきで出す。事実はエージェントが調べ、決定はユーザーが行う）は、Matt Pocock のスキル集の `grilling` に倣った（`mattpocock/skills:skills/productivity/grilling/SKILL.md@5863806`、MIT。https://github.com/mattpocock/skills ）。答えを Issue に記録し、`ready` の Issue にするところは、このリポジトリの流れ（ADR-0003、ADR-0011）に合わせて足した。
