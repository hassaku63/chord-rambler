# 0012. 説明の文は、取り消さずに詳しくできる単純化だけを許す

- 日付: 2026-11-15
- 状態: Accepted（所有者の判断は #42）

## 文脈

コンセプトは、説明に教育上の単純化を許すが、音楽的な意味に明白な誤りや矛盾を含めない、と求めている（`docs/product/concept.md` の 1 章）。どこからが誤りかの基準がなかった。基準がないと、エンジンの事実・カタログのデータ・文の型を書くたびに、その場の感覚で決めることになる。エンジンの実装の前に決める（#8）。

- 最初の範囲では、候補も説明もルールとカタログが作る。生成 AI は使わない。
- 問い合わせが返す事実は、項目ごとに根拠の種類（定義、計算、流儀、慣習、連想）を持つ（ADR-0005）。
- 流儀の文書は、テンションを「濁りやすい」と述べ、セカンダリー・ドミナントの名前を進む先で変えない。どちらも、あとで取り消さずに済む形になっている。
- 「取り消さずに済むか」という基準そのものを述べた一次情報は、見つけていない。教育の文献（Bruner の「知的に誠実な形」、あとで学び直しが要る単純化への批判）は、二次の情報で読んだ範囲では、この向きを支持する。

## 決定

規則の全体は `docs/architecture/explanations.md` に書く。要点は次のとおり。

1. **基準は、詳しく言い直すときに取り消さずに済むこと。** このアプリで作れる進行の中に、文が偽になる場合があってはいけない。
2. **根拠の種類で言い方を変える。** 定義と計算は言い切る。流儀は呼び名か働きとして述べる。慣習は頻度として述べ、正誤にしない。連想は傾向として述べ、言い切らない。
3. **許さない誤りは 5 つ。** 鳴る音と合わない。前後や位置についての主張が進行と合わない。根拠より強く言う。呼び名の誤用。1 つの画面の中での食い違い。
4. **流儀による読みは、呼び名や働きとして述べる。** 別の立場があることは、開いて見る側に出す。
5. **ユーザーの選択を「誤り」と言わない。** 事実と注意（「定番ではない」「変則」「濁りやすい」）までを述べ、実際の動きのとおりに説明する。
6. **言えないときは、計算できる事実だけを述べる。** それらしい名前を付けない。
7. **誤りは仕組みで止める。** 誤りごとの検査を、まとまりを実装するスライスの受け入れ条件に入れる。機械で見ないものは、レビューと観察の Issue で拾う。
8. **説明の粒度は、ここでは決めない。** 最初の文ができてから、使って決める。

## 検討した選択肢

- **厳密にする**（流儀によることと別の読みを、文に毎回書く）: 誤解の余地がいちばん小さい。文が長くなり、初心者が要点を読み取りにくい。コンセプトが許した単純化を、ほぼ使わないことになる。
- **緩くする**（データと食い違うものだけを誤りとし、言い方は決めない）: 文の型を自由に書ける。「sus4 は浮遊感を生む」のような言い切りが通り、意図と手段を一対一にしない原則と、理論の説明と印象の区別を、文が崩す。
- **評価の言葉を一切出さない**: 押しつけはなくなる。なぜ耳に引っかかるかの手がかりも出なくなり、流儀の文書が採った「濁りやすい」の注意と合わない。
- **評価まで出す**（「不自然に聞こえやすい」）: 助言としては強い。慣習を正誤のように伝えやすい。

## 結果

- 文の型と事実を書く人が、同じ基準で判断できる。`ready` の Issue に、従う判断として書ける。
- 誤りの大半を、エンジンのテストで止められる。文の型ごとに根拠の種類を決める手間が増える。
- 「取り消さずに済むか」の判定は、最後は人の読みに頼る。
- 生成 AI を入れるとき（#5）も、同じ線を使う。AI の文をどう照合するかは、そのときに決める。
- 再検討の条件: 文末の違いが使う人に伝わっていないと分かったとき。基準に照らして判定の割れる文が、繰り返し出てきたとき。
