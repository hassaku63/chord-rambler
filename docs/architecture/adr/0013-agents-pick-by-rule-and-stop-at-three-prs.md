# 0013. エージェントは規則で Issue を選び、未マージの PR が 3 本で止まる

- 日付: 2026-11-15
- 状態: Accepted（所有者の判断は #40）

## 文脈

開発をエージェント自身で自律的に回したい（所有者の相談、#40）。今は、次に着手する `ready` の Issue を所有者がそのつど指示し、判断待ちの Issue も所有者が頼んで順に見ている。

- 作業は、企画（`proposal`）、所有者の判断、`ready` の Issue、実装の順に進む（ADR-0003）。`ready` の Issue には判断を残さない（ADR-0011）。
- どれを先にやるかは優先度の判断で、所有者のもの。エージェントが Issue を読んで重要さを判断すると、所有者の判断が紛れ込み、理由をあとから検証しにくい。
- エージェントが PR を開き続けると、レビューが追いつかず、あとの PR が前の PR に依存しやすくなる。
- GitHub のアカウントは所有者の 1 つで、エージェントの PR も同じアカウントで開く。エージェントのブランチは `claude/` で始まる。
- 人の手を離れたループ（`/goal`、`/loop`、予定のタスク）は、止まる条件が働くことを確かめてからでないと危うい。

## 決定

1. **エージェントは、`ready` の Issue を規則で選んで着手してよい。** 優先度を自分で判断しない。`proposal` と `needs-decision` の Issue には着手しない。
2. **順番は、`priority:high` のラベルが付いたものが先、同じなら番号の小さい順。** ラベルは所有者が付ける。本文の「依存」に書いた Issue が開いているものと、閉じる PR がすでに開いているものは選ばない。
3. **エージェントが開いた未マージの PR が 3 本になったら、新しい Issue に着手せず、所有者にマージか方針の判断を仰ぐ。** head のブランチ名が `claude/` で始まる開いた PR で数える。
4. **人の手を離れたループは、今は使わない。**

規則と止まる条件は `docs/dev/workflow.md` に書く。

## 検討した選択肢

- **優先度もエージェントが判断する**: 所有者が順を付ける手間がなくなる。所有者の判断が紛れ込み、なぜその順だったかをあとから検証しにくい。
- **上限を置かない**: エージェントが止まらずに進む。レビュー待ちが積み上がり、あとの PR が前の PR に依存しやすくなる。
- **上限を 2 本にする**: より早く止まる。1 PR を小さく保っているので、待ちが増えやすい。
- **段階の優先ラベル（high / medium / low）を置く**: 細かく並べられる。付け直す手間が増え、ふだんは古い順で足りる。
- **ラベルを置かず、常に古い順にする**: 仕組みが最も小さい。急ぐものを先にするたびに、所有者が指示し直すことになる。

## 結果

- 所有者は、急ぐものに `priority:high` を付けるだけで、順を指示しなくてよくなる。
- エージェントは、止まる条件に当たると所有者に返す。止まる回数が増えるぶん、所有者のレビューとマージの速さが進み方を決める。
- 規則は機械で検査しない。エージェントが規則を守ったかは、PR に書いた選んだ理由で確かめる。
- 再検討の条件: 止まる条件が働くことを何度か確かめたあと、人の手を離れたループを検討するとき。上限で止まることが続き、所有者のレビューが詰まっているとき。
