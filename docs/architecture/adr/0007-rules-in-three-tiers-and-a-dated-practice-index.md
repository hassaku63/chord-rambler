# 0007. 規則は 3 段で持ち、索引は出どころと確認日で鮮度を見る

- 日付: 2026-11-15
- 状態: Accepted

## 文脈

機械で検出できる規約は `make check` で強制する（ADR-0004）。設計や実装の良し悪しには、機械で検出できないものがある。言語やライブラリの流儀、テストの書き方、抽象を足すかどうかの判断など。これを設計・実装・レビューのときに引ける形で持ちたい（#16）。

手元に持つことには 2 つの危険がある。

- 一般的な流儀を書き並べると、エージェントが学習済みで持つ知識の重複になり、読まれない長文が増える。
- 手元に資料を持ったために、出どころの推奨が変わっても気づけず、古い写しを信じ続ける。

機械が検出できるのは、時間が経ったこと、依存の版が変わったこと、出どころが変わった・消えたことまで。助言がもう正しくないかどうかは、出どころを読み直して判断するしかない。

## 決定

1. **規則を 3 段で持つ。** 機械の検査（`make check`）、規約（このプロジェクトが決めたこと。`AGENTS.md`、`docs/`、ADR）、索引（決める前に当たる知見。`.claude/skills/practices/`）。上の段に上げられるものは上げ、上げたら下の段から消す。
2. **索引に載せるものを絞る。** 版で変わるもの、流儀が割れるもの、やりがちな逆、レビューの観点。本文や例のコードは写さず、要点と判断の問いまでを持つ。項目は 40 個まで。載せなかったものは理由と一緒に残す。
3. **項目は出どころと確認日を持つ。** 出どころは一次情報の URL。Git で公開されていれば、リポジトリ・ファイル・コミットも書く。関係する依存と版、出どころを実際に開いた日、見直しの間隔を、スクリプトが読める書き方で持つ。
4. **古くなったことに、3 つの段で気づく。**
   - `make check`: 項目の形。依存が入ったあとは、項目の対象の版と今の依存の版の食い違い、項目のない依存。コミットが同じなら結果が同じものだけを置く。
   - 月次の定期のジョブ: 見直しの期限、リンク切れ、記録したコミットのあとの出どころの変更、依存の新しい大きな版。指摘があれば Issue を 1 つ作る。
   - 四半期の総点検: 所有者が始める。出どころを開き直し、依存のリリースノートを読んで足りない項目を拾い、当たられなかった項目を削る候補にする。
5. **期限を過ぎた項目を根拠に使うときは、先に出どころを開き直す。**
6. **引くきっかけを手順に結びつける。** `AGENTS.md` のガードレール、PR テンプレートの欄、レビューの観点。

## 検討した選択肢

- **持たない**: 維持の費用も、古くなる写しもない。版による推奨の変化、流儀の選択、やりがちな逆を拾えない。
- **規約の文書に全部書く**: 強制力は強い。決めていないことまで規則になり、長くなって読まれず、出どころがないので古くなっても気づけない。
- **外の文書へのリンク集だけを持つ**: 維持が軽い。どの場面で何を見るかが分からず、引かれない。
- **日付による検査を `make check` に入れる**: 期限切れを確実に止められる。同じコミットが昨日は通り今日は落ち、関係のない PR を止める。

## 結果

- 依存の大きな版を上げる PR は、関係する項目を確かめ直すまで通らない（依存が入ったあと）。
- 出どころが変わらないまま世の中の合意が変わった場合と、Git のソースがない出どころの変更は、総点検でしか拾えない。
- 項目を足すたびに、出どころを開く手間がかかる。これは意図どおり。
- 再検討の条件: 総点検で、当たられなかった項目が大半を占めたとき。索引をやめるか、載せる種類を絞り直す。
