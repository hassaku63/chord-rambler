# 0008. エンジンは Go の API、画面は React と TypeScript

- 日付: 2026-11-15
- 状態: Accepted

## 文脈

エンジンの構成（ADR-0005）、進行のモデル（ADR-0006）、開発の規則（ADR-0007）が決まり、実装を始めるために言語・実行する場所・道具を決める（#23）。

- 最初の範囲は生成 AI を使わないので、鍵を持つサーバーは最初は要らない。エンジンをブラウザの中で動かす構成も取れる。
- 所有者は、次の理由でエンジンをサーバー側の Go に置くことを選んだ。
  - 純粋なドメインのロジックを、Go の方が堅く書きやすい。
  - AI、保存、共有などで、あとでサーバーが要る前提である。
  - API を挟むことで、エンジンを画面から独立した部品にしたい。
- 確かめた版の制約（2026-11-15、npm のレジストリと go.dev）: OpenAPI から TypeScript の型を生成する openapi-typescript 7.13.0 は、TypeScript 5 系を求める。typescript-eslint 8.72.2 が受け付ける TypeScript は 6.1 未満。Go の最新は 1.27.4。

## 決定

1. **エンジンは Go で書き、HTTP の API の向こうに置く。** サーバーは状態を持たない。画面が進行を持ち、問い合わせのたびに進行を送る。
2. **画面は React 19 と TypeScript。** ビルドは Vite、テストは Vitest と Testing Library、lint は ESLint と typescript-eslint、整形は Prettier。状態管理のライブラリは入れない。スタイルは素の CSS。
3. **API の契約は OpenAPI の文書を正とする。** Go 側は、登録したルートと契約の一致をテストで強制する。TypeScript 側は、契約から生成した型を使い、生成物の鮮度を検査で強制する。型を手で書かない。このため TypeScript は 5.9 系にする。
4. **Go は標準ライブラリを基本にする。** `net/http` のメソッド付きのパターン、`log/slog`。フレームワークは使わない。
5. **エンジンのまとまりを、Go のパッケージに対応させる。** 依存の向き（下は上を知らない）と、エンジンが入出力を持たないことを、lint で強制する。
6. **慣習と連想のカタログは JSON のファイル。** サーバーに埋め込み、読み込み時にエンジンが検証する。テストがすべてのカタログを読み込んで検証する。
7. **音は、画面が Web Audio API を直接使って鳴らす。** エンジンは音符の列を返す。音源のライブラリは、音色を検討するときに別の ADR で決める。
8. **動かし方は、手元のコマンドとコンテナの両方を用意する。** Dockerfile と compose で API と画面を起動でき、CI がイメージのビルドとスモークを走らせる。公開先は決めない。
9. **道具の版は `.tool-versions` に置く。** Go 1.27 系、Node 22 系。

配置:

| 場所 | 役割 |
| --- | --- |
| `backend/cmd/server` | エントリポイント。配線だけ |
| `backend/internal/<まとまり>` | エンジン。`docs/architecture/engine.md` の土台とまとまりごとに 1 パッケージ |
| `backend/internal/httpapi` | HTTP のハンドラ。decode、エンジンの呼び出し、encode だけ |
| `frontend/src/app` | アプリの枠 |
| `frontend/src/features/<name>` | 機能ごとの縦の切り方（UI、hooks、状態） |
| `frontend/src/shared` | API のクライアント、共通の UI |
| `docs/` の下の API の文書 | API の契約（OpenAPI） |

## 検討した選択肢

- **すべて TypeScript で、エンジンをブラウザの中で動かす**: 候補と試聴に通信が入らず、言語が 1 つで契約の仕組みが要らない。あとでサーバーが要る前提と、エンジンを画面から独立させたいという方針に合わない。
- **Go か Rust のエンジンを WebAssembly にして、ブラウザの中で動かす**: 通信なしで動く。ビルドの道具が増え、境界で値を詰め替える層が要り、デバッグが難しくなる。
- **Go の型から TypeScript の型を生成する**: 契約の文書を手で書かずに済む。道具の選定が要り、判別共用体のような型を表しにくい。

## 結果

- 候補の問い合わせのたびに通信が入る。応答には、候補・読み・試聴用の音符を一度に載せ、往復の回数を減らす。
- 動かすにはサーバーが要る。手元ではコマンド 2 つ、またはコンテナで起動する。
- 契約・生成した型・ルートの一致の検査という、言語をまたぐ仕組みの費用がかかる。
- エンジンを、画面以外（コマンド、評価のスクリプト、別のクライアント）からも使える。
- 進行の型は、Go と TypeScript の両方に現れる。TypeScript 側は生成した型を使い、進行の操作のロジックを画面に写さない。
- TypeScript を 5.9 系に留める。型の生成の道具が新しい系に対応したら、上げる。
- 再検討の条件: 通信の待ち時間が「選んですぐ聴く」体験を損なうと観察されたとき。
