# 0019. 画面は、キャンバス・帯・文脈の欄の骨組みに、同じ進行への 2 つのタブを載せる

- 日付: 2026-11-18
- 状態: Accepted（所有者の判断は #196）

## 文脈

画面の構成（2 つの体験を 1 つの画面にまとめるか、モードを分けるか）は、コンセプトの未決定事項だった。今の画面は仮の配置で、作り直してよいことになっていた（#110、#148）。画面 1〜4 を 1 列に縦に並べ、体験 A と体験 B を同じ画面に置いていた。

所有者の観察（#196）:

- 今の画面は、操作の体験に大きな改善の余地がある。
- 骨組みとしては、所有者が ChatGPT Sites で作ったスケッチ（リポジトリの文書だけから作ったもの）の方が、スタート地点として優れている。
- グラフ型では、キャンバスの上で選べてほしい。次の候補を選ぶ体験に、遊び感がほしい。

検討では、この画面で満たす体験を E1〜E5 に整理した（表は `docs/product/screen-promise.md` の 1）。今の画面を、main の 15bda43、1440×900 で辿って測った事実:

- E1: 末尾の候補は C で 31 個で、まとまりごとに縦に並ぶ。最初の視野に入るのは 8 行。理由は略号の並びで、期待する印象の説明はない。
- E3: 枠を選ぶと、詳しい札・変形・枠を埋める候補が、末尾に足す候補の上に差し込まれる。ページの高さは 1,475 px から 2,796 px になり、末尾に足す作業と枠を直す作業の行き来に約 1,400 px のスクロールが要る。フレーズの区切りと小節の目盛りは見えない。
- E4: 4 枠に役割を置くのに 8 操作かかる。区間の単位で計画する操作はなく、埋めても次の空いた枠へ進まない。
- E5: 取り消し、並べ替え、途中への挿入がない。C で C・Am・F・G7 を置いて調を D に変えると、和音名はそのままで、読みが ♭VII・v・♭III・IV7 に変わる。コンセプトの 3.4 の移調（音程の関係を保って和音名が変わる）とは逆。

Sites のスケッチ（2026-11-18 の版）: https://chord-rambler-design-study.onwardhazel3.chatgpt.site

- 左にキャンバス（ノードを矢印でつなぐ）と、小節と再生の帯。計画のタブでは、右に、選んでいる小節に追随する欄がある。2 つのタブが、同じ小節の並びを編集する。
- 探索のタブでは、候補 3 つが末尾のノードから枝として伸びる。枝を選ぶと、しくみと印象、試聴、確定の操作が出る。確定すると枝が本線のノードになり、新しい末尾から次の枝が伸びる。
- 元に戻すがある。調を変えると移調する。
- 候補 6 種と説明の文は手書きの固定データで、1 小節 1 和音に固定。
- 中身に誤りと食い違いがある。「B♭maj7：同主短調から借りられる和音」は誤り。C の自然短音階の VII は B♭7（B♭ D F A♭）で、B♭maj7 は、`docs/architecture/theory-conventions.md` の 3 の規則では、ミクソリディアンとドリアンから借りる。役割の語は、コンセプトの 4 章の例（導入、提示、展開など）で、`docs/glossary.md` の構造的な役割と色合いの役割ではない。

## 決定

1. **骨組み。** スケッチの骨組みを土台にし、今のエンジンの中身（候補、読み、変形、長さ、根拠の印）を載せ替える。
   - キャンバス（流れ）、帯（時間）、選んでいるものに追随する文脈の欄を、1 つの画面に収める。
   - 2 つの体験は、同じ進行に対する 2 つのタブにする。タブを切り替えても、進行は同じ。
   - 候補を採るまでの流れは、選ぶ → 理由を読む → 聴く → 採る。
   - 元に戻す操作と、移調（コンセプトの 3.4）を持つ。
2. **グラフ型の操作は、キャンバスの上で枝から選ぶ。** スケッチの形に、次の 4 点を足す。
   - 触れると鳴る: 枝を選ぶかフォーカスすると、すぐ「前の枠 + 候補」が鳴る。確定は Enter かダブルクリック。
   - 枝に一言: 枝に、期待する印象の一言を出し、開かずに見比べられるようにする。
   - 探索の足跡: 1 歩前の分岐を薄く残し、選び直せるようにする。
   - 線が意味を運ぶ: 確定した線に、読みの判定（解決、終止）を形と語で載せる。
3. **前提の 2 つは、器と並行して企画にする。** 候補を絞る規則（#203）と、説明の文（#204）。決まるまで、器は今の候補の並びの先頭から数個で動かす。
4. **今の画面は置き換える。** 新しい器ができたら消す。エンジンの確かめは、API のテストと E2E に任せる。
5. **スケッチは参照に留める。** 骨組みと操作の発想だけを採る。上の誤り（B♭maj7 の借り先）と語の食い違い（役割）は採らない。語は `docs/glossary.md`、借り先は `docs/architecture/theory-conventions.md` の 3 に従う。
6. **目標の画面の約束を `docs/product/screen-promise.md` に書く。** 器から先の Issue を `ready` にするときと、E2E と画面レビュー（`.claude/skills/ui-review/SKILL.md`）の基準にする。

## 検討した選択肢

- **A. スケッチの骨組みを土台にする**（採った）: 全体と選んでいる 1 点が 1 つの視野に入る（E3）。エンジンの中身の載せ替えと、器の作り直しが要る。
- **B. 今の画面を直していく**: 区画を横に並べ、候補を絞る。手戻りは小さい。器の発想が変わらないので、E3 と遊び感に届きにくい。
- **C. 体験ごとに別の画面にする**: 画面ごとの操作は単純になる。コンセプトの 4 章の「同じ進行のモデルに対する別の操作」から遠くなる。
- **グラフ型の 4 点を採らない**（試聴を別のボタンにする、選んでから説明を読む、元に戻すだけ、矢印は飾り）: 器は小さくなる。触っては聴く繰り返しと、開かずに見比べること、つながりの意味が、遊びと学びの核から抜ける。
- **器を先に作り、前提をあとで決める**: 器は早く動く。説明の文を手で書くと、スケッチの B♭maj7 のような誤りを持ち込む危険がある。並行にし、器は今の候補で動かす。
- **今の画面を、エンジンを確かめる画面として残す**: 手で確かめる場所が残る。2 つの画面を保つことになり、確かめは API のテストと E2E でできる。

## 結果

- 全体（キャンバスと帯）と、選んでいる 1 点（文脈の欄）を、スクロールなしで同時に見られる。
- タブは状態を持つ（モード）。どちらのタブかを取り違えないよう、手がかりと操作の名前を約束の文書で縛る。
- 枝の数と選び方、枝の一言と説明の文は、#203 と #204 が決まるまで暫定で動く。
- 今の画面の検査（`frontend/e2e/`）と `docs/architecture/screen.md` は、器に置き換えるときに書き直す。
- 直接操作の根拠は、HCI の索引で「外したもの」にある。採るときに、出どころを取り直す。
- 前提は PC の横長の画面。狭い幅の配置は、この判断に含まない。
- 再検討の条件: 所有者が器で進行を作り、骨組みそのもの（タブで分けること、文脈の欄が追随すること）への不満が観察に出たとき。
