# 0004. 検査は `make check` に集め、CI は同じターゲットを呼ぶ

- 日付: 2026-11-15
- 状態: Accepted

## 文脈

検査が手元と CI で違うと、手元で通ったものが CI で落ち、エージェントは原因を再現できない。検査が増えると、何が何を防いでいるかが分からなくなり、効かない検査が費用だけを残す。

## 決定

1. **`make check` がすべての門。** 手元で走らせられる検査は、すべてこのターゲットに入れる。CI は同じ Makefile のターゲットを呼び、検査の中身をワークフローに書かない。
2. **必須チェックは 1 つ。** CI の `required (make check)` だけをマージの条件にする。ジョブを分けるときも、結果をこの 1 つにまとめる。
3. **検査の一覧を 1 箇所に持つ。** 検査を足すときは `docs/dev/harness.md` に 1 行（防ぐもの、個別の実行方法、場所）を足す。手元で走らせられない検査（ネットワークやコンテナが要るもの）は、その理由と一緒に載せる。
4. **道具の版は `.tool-versions` に置く。** Makefile と CI がそこから読む。
5. **ワークフローのアクションはコミットの SHA で固定する。** 行末に版を書き、更新は Dependabot に任せる（GitHub の Security hardening for GitHub Actions の「Using third-party actions」）。
6. **検査は見直して減らす。** 長いあいだ何も捕まえず費用だけがある検査は、削除の候補にする。

## 検討した選択肢

- **CI のワークフローに検査を直接書く**: 設定が 1 つで済むが、手元で再現できず、エージェントが push して結果を待つ往復が増える。
- **pre-commit のフックで強制する**: コミットの前に落とせるが、エージェントの環境ごとに導入が要る。`make check` を完了の条件にすれば足りる。

## 結果

手元の `make check` が通れば CI も通る、と期待できる。検査を足すたびに一覧を直す手間が増える。検査が増えて `make check` が遅くなったら、変更に関係するジョブだけを走らせる仕組みを、必須チェックを 1 つに保ったまま足す。
