# 0003. 作業は Issue と PR で回し、文書に作業の一覧を持たない

- 日付: 2026-11-15
- 状態: Accepted

## 文脈

何を作るか、次に何をするかを、人間とエージェントが同じ場所で読める必要がある。エージェントが思いつきで機能を足すと、スコープが広がり、所有者が判断する機会がなくなる。一方、作業の一覧をリポジトリの文書にも持つと、Issue と二重になり、どちらかが古くなる（ADR-0002 の「事実は 1 箇所」に反する）。

## 決定

作業の一覧は GitHub の Issue だけに置く。

- **観察**（`observation`）: 見つけた問題や思いつき。原因や解決策はなくてよい。
- **企画**（`proposal`、判断待ちは `needs-decision`）: 観察や未決定事項を検討した結果。選択肢、推奨、決めてほしいこと、スライス案。
- **着手できる作業**（`ready`）: 受け入れ条件が決まった 1 スライス。所有者が判断したものだけに付ける。
- 1 PR = 1 Issue。PR は `main` へのマージで Issue を閉じる。`main` には直接 push しない。
- Issue と PR の本文は現在の状態に保ち、見解の変化や訂正はコメントで足す。

## 検討した選択肢

- **リポジトリに backlog の文書を持つ**: ネットワークなしで読め、並び順を PR でレビューできる。Issue と内容が二重になり、同期の手間と、ID の検査や完了行の刈り込みといった維持の仕組みが要る。
- **GitHub Projects で管理する**: 並び順と状態を持てるが、エージェントの道具から読み書きしにくい。Issue の数が増えて並び順が要るようになったら検討する。

## 結果

作業の状態は Issue を見れば分かり、文書は作業の進み具合を書かなくてよい。エージェントは GitHub に届かないと次の作業を選べない。並び順は `ready` のラベルと所有者の指示で決める。再検討の条件: `ready` の Issue が常に多数あり、順番を決めるのに毎回所有者の指示が要るようになったら、並び順を持つ仕組みを足す。
