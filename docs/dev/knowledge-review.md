# 知識の点検

手元に持っている知識（プラクティスの索引、標準の索引、HCI の索引、流儀の出どころ）と、依存・ベースイメージ・検査が古くなったことに気づき、確かめ直す手順。決定は ADR-0007、ADR-0015、ADR-0018。

対象:

- `.claude/skills/practices/index.md`（プラクティスの索引）
- `.claude/skills/standards/index.md`（標準の索引。期限を過ぎた項目は、報告で「標準の索引: 」を前に付けて挙がる）
- `.claude/skills/hci/index.md`（HCI の索引。期限を過ぎた項目は、報告で「HCI の索引: 」を前に付けて挙がる。期限は「確認日」の欄で見る。「未確認」の項目は期限を持たないので、総点検で開き直す）
- `docs/architecture/theory-conventions.md`（読みと表記の流儀の出どころ）
- 依存（`frontend/package.json`、`backend/go.mod`）と、`Dockerfile` の実行用のベースイメージ（総点検だけで見る）
- `docs/dev/harness.md` の検査（総点検だけで見る）

## 月次の報告

`.github/workflows/knowledge-review.yml` が毎月 1 日に走る（手動でも走らせられる）。`scripts/knowledge-staleness.sh` が次を調べ、指摘があれば `knowledge-review` ラベルの Issue を 1 つ作る。すでに開いていれば、本文を新しい報告で置き換える。

| 報告の節 | 意味 | すること |
| --- | --- | --- |
| 見直しの期限を過ぎた項目 | 確認日から、項目の間隔を過ぎた | 出どころを開き直す（下の手順） |
| 開けない出どころ | URL が 404 などを返す | 移った先を探して直す。無くなっていれば、別の一次情報に替えるか、項目を消す |
| 別の場所へ移った出どころ | URL が別の場所へ転送される | 新しい URL に直す |
| 記録したコミットのあとに変わったソース | Git のソースのファイルが、記録したコミットより新しい（プラクティスの索引だけ） | 報告の差分のリンクを開き、要点が変わったかを読む（下の手順） |
| 確かめられなかったソース | ファイルが移ったか、API が答えなかった | リポジトリを開いて、ファイルの今の場所を確かめる |
| 自動の確認を拒んだサイト | サイトが機械の取得を拒んだ | 参考。ほかの指摘と一緒に、人が開いて確かめる |

手元で走らせる:

```bash
bash scripts/knowledge-staleness.sh            # 全部（ネットワークが要る）
bash scripts/knowledge-staleness.sh --offline  # 期限だけ
```

## 項目を確かめ直す

1. 出どころを開く。Git のソースがあれば、記録したコミットとの差分を読む。
2. 「何を言っているか」「確からしさ」（標準の索引では「何を決めているか」「状態」）が、今の出どころと合っているかを確かめる。HCI の索引では、開いたものを確認日の欄に書き直す。
3. 合っていれば、確認日を今日にする。ソースのコミットも今のものに直す。
4. 合っていなければ、項目を直す。出どころが主張を取り下げていれば、項目を消して「外したもの」に理由を残す。
5. 「このプロジェクトの立場」が規約や ADR を指している項目を直したときは、指している先も同じ PR で見直す。

出どころを開かずに確認日だけを更新しない。開けなかったら、開けなかったことを PR に書いて、確認日はそのままにする。

## 総点検（四半期。所有者が始める）

月次の報告は、時間が経ったことと、出どころが変わった・消えたことしか分からない。出どころが変わらないまま世の中の合意が変わった場合や、手元に無い知識には気づけない。それを拾うのが総点検で、所有者が始め、結果を受け取る。作業はエージェントに任せてよい。

1. `knowledge-review` の Issue に挙がった項目と、HCI の索引の「未確認」の項目を、上の手順で確かめ直す。
2. 索引の全項目について、PR の「当たった索引の項目」に一度も挙がらなかったものを一覧にする。削る候補として所有者に示す。
3. 索引の節ごとに、「この半年のレビューで繰り返し出た指摘で、項目にないもの」を挙げる。項目にするか、lint にするかを決める。
4. `docs/architecture/theory-conventions.md` の「確かめていないこと」を読み、確かめられるようになったものを確かめる。
5. 依存とベースイメージの陳腐化を挙げる。
   - `frontend/package.json` の直接の依存と Go のモジュールのうち、非推奨になったもの（npm の deprecated の表示など）と、長く公開のないもの。版の遅れは Dependabot が受け持つので、ここでは見ない。
   - `Dockerfile` の実行用のベースイメージのタグが、出どころのサポートの一覧に載っているか（distroless は README と SUPPORT_POLICY.md、nginx の像は公開元の案内）。Dependabot は同じタグの中の digest しか更新しないので、タグのサポートが終わっても PR は来ない。
6. `docs/dev/harness.md` の各行を見直し、前回の総点検からあとに何も捕まえていない検査を、削る候補として所有者に示す。
7. 結果を 1 つの PR にし、`knowledge-review` の Issue を閉じる。
