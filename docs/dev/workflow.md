# 開発ワークフロー

人間でも AI エージェントでも同じ手順で進める。規則の要約は `AGENTS.md`、ここは詳細と理由。

## 開発ループ

```
観察（Issue） → 検討（企画 Issue） → 所有者の判断 → ready の Issue
                                                        │
ready の Issue を 1 つ → 受け入れ条件を確認 → テストを書く → 実装 → make check
                                                                      │
                 Issue を閉じる ← PR（テンプレート） ← 文書を直す ←────┘
```

上の段は、何を作るかが決まっていないときだけ通る。所有者がすでに決めたことは、`ready` の Issue から始めてよい。

## Issue の使い方（ADR-0003）

| ラベル | 意味 | 誰が付けるか |
| --- | --- | --- |
| `observation` | 見つけた問題、思いつき。原因や解決策はなくてよい | 誰でも |
| `proposal` | 観察や未決定事項を検討した結果。選択肢と推奨を書く | 検討した人（エージェントを含む） |
| `needs-decision` | 所有者の判断を待っている | 企画を書いた人。判断が出たら外す |
| `ready` | 受け入れ条件が決まり、着手できる 1 スライス | 所有者、または所有者の判断を受けた人 |

- 企画は実装しない。決めてほしいことを所有者にしか決められないものに絞り、答えは Issue のコメントで受ける。
- Issue と PR の本文は現在の状態に保つ。見解の変化や訂正はコメントで足す。
- コンセプトの未決定事項（`docs/product/concept.md` の 8 章）は、1 つずつ企画の Issue で検討し、決まったら ADR に記録して文書を直す。

## 1 スライスの進め方

1. `ready` の Issue を 1 つ選ぶ。受け入れ条件が曖昧なら、実装せずに Issue で質問する。
2. テストを先に書く（または同じコミットで書く）。書き方は下の「テストの書き方」。
3. 実装する。既存のファイルは全体の書き換えではなく差分で直す。
4. `make check` を通す。lint を無効にしたり、テストをスキップしたりして通さない。
5. 影響する文書を直す（`docs/dev/docs-hygiene.md` の自己点検）。設計判断をしたら ADR を足す。
6. PR を開く前に自己レビューをして、要約を PR の「レビューの見どころ」に書く。

## テストの書き方

| 層 | 手段 | 例 |
| --- | --- | --- |
| エンジン（`backend/internal/` のまとまり） | テーブル駆動の単体テスト。既知の理論の事実をデータとして並べ、出どころをコメントに書く。不変量には性質によるテスト | C major のダイアトニックの三和音、移調して戻すと元に戻る |
| `backend/internal/httpapi` | `httptest` のレコーダーで、JSON の形とステータスを確かめる | 存在しないパスが problem の文書を返す |
| `backend/internal/config` | テーブル駆動。環境変数を読む関数を差し替える | 範囲の外の `PORT` がエラーになる |

判断に迷ったら、プラクティスの索引（`.claude/skills/practices/index.md`）の 1 節を引く。

## 完了の定義

- 受け入れ条件をすべて満たしている。
- `make check` が通り、CI の `required (make check)` が緑。
- 振る舞いの変更にテストがある。
- 言及が変わる文書を直してある。
- PR に、スコープ外にしたことが書いてある。

## コミットと PR

- Conventional Commits。1 PR = 1 Issue = 1 スライス。
- PR 本文は `.github/pull_request_template.md` に従う。
- `main` に直接 push しない。`git push --force` をしない。
