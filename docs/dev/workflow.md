# 開発ワークフロー

人間でも AI エージェントでも同じ手順で進める。規則の要約は `AGENTS.md`、ここは詳細と理由。

## 開発ループ

```
観察（Issue） → 検討（企画 Issue） → 所有者の判断 → ready の Issue
                                                        │
ready の Issue を 1 つ → 受け入れ条件を確認 → テストを書く → 実装 → make check
                                                                      │
                 Issue を閉じる ← PR（テンプレート） ← 文書を直す ←────┘
```

上の段は、何を作るかが決まっていないときだけ通る。所有者がすでに決めたことは、`ready` の Issue から始めてよい。

次の `ready` の Issue を規則で選んで着手するところは、スキル `/next-issue`（`.claude/skills/next-issue/SKILL.md`）で行える。

## Issue の使い方（ADR-0003）

| ラベル | 意味 | 誰が付けるか |
| --- | --- | --- |
| `observation` | 見つけた問題、思いつき。原因や解決策はなくてよい | 誰でも |
| `proposal` | 観察や未決定事項を検討した結果。選択肢と推奨を書く | 検討した人（エージェントを含む） |
| `needs-decision` | 所有者の判断を待っている | 企画を書いた人。判断が出たら外す |
| `ready` | 受け入れ条件が決まり、着手できる 1 スライス | 所有者、または所有者の判断を受けた人 |
| `priority:high` | `ready` の中で、先に着手する | 所有者 |

- 企画は実装しない。決めてほしいことを所有者にしか決められないものに絞り、答えは Issue のコメントで受ける。
- 判断待ちの問いを所有者に出し、答えを記録して `ready` の Issue にするまでは、スキル `/grill`（`.claude/skills/grill/SKILL.md`）で行える。
- Issue と PR の本文は現在の状態に保つ。見解の変化や訂正はコメントで足す。
- コンセプトの未決定事項（`docs/product/concept.md` の 8 章）は、1 つずつ企画の Issue で検討し、決まったら ADR に記録して文書を直す。

## `ready` の Issue に書くこと（ADR-0011）

`ready` の Issue は、企画の段階から実装の段階への引き継ぎの文書。実装する人（軽いモデルのエージェントを含む）が、新しく判断せずに進められるように書く。

| 項目 | 書くこと |
| --- | --- |
| 目的 | 何のためのスライスか。元の企画の Issue |
| 受け入れ条件 | 確かめられる形で。手で確かめることがあれば、その手順 |
| 決まっている判断 | 従う ADR、`docs/architecture/` の文書、Issue のコメントの判断 |
| 触る場所 | 足す・変えるファイルやパッケージ |
| スコープ外 | やらないこと。見つけたら Issue にすること |
| 当たる索引の項目 | `.claude/skills/practices/index.md` の項目名 |
| 依存（任意） | 先に閉じている必要のある Issue。`blocked by #N` の形で書く |

次のどれかに当たるなら、`ready` にしない。企画の Issue に戻して、所有者の判断を受ける。

- 選択肢が 2 つ以上あり、どれを採るかが決まっていない。
- 音楽理論の立場（流儀）を新しく選ぶ必要がある。
- 依存の追加や、API の形の変更を含み、その判断がまだない。

## 次の Issue の選び方と、止まる条件（ADR-0013）

エージェントは、次の規則で `ready` の Issue を 1 つ選ぶ。優先度を自分で判断しない。`proposal` と `needs-decision` の Issue には着手しない。

1. 開いている `ready` の Issue から、次を除く。閉じる PR がすでに開いているもの（着手済み）。「依存」に書いた Issue が開いているもの。
2. `priority:high` のラベルが付いたものを先に、同じなら番号の小さい順に並べ、先頭を選ぶ。
3. 選んだ Issue と、どの規則で先頭になったかを、PR に書く。

次のどれかに当たったら、止まって所有者に返す。

- エージェントが開いた未マージの PR が 3 本ある（head のブランチ名が `claude/` で始まる開いた PR で数える）。一覧を示し、マージか方針の判断を仰ぐ。
- 選べる `ready` の Issue がない。`needs-decision` の Issue と、依存で止まっている Issue の一覧を示す。
- 実装の途中で判断が要った。実装を止めて Issue のコメントに書く。判断を埋めない。

人の手を離れたループ（`/goal`、`/loop`、予定のタスク）は、今は使わない。

## 段階ごとのモデルの目安（ADR-0011）

強制ではない。費用と質の釣り合いの目安。

| 段階 | 主のモデル | 助言役 |
| --- | --- | --- |
| 企画、調査、設計（`proposal` の Issue、ADR、`ready` の Issue を書く） | 最も強いモデル | なし（主が最上位なので要らない） |
| `ready` の Issue の実装 | 一段軽いモデル | 強いモデル。やり方を決める前、同じ失敗が続くとき、完了の前に相談する |
| 定型の作業（文書の同期、名前の変更、依存の更新） | 軽いモデル。努力の度合いを下げてよい | なし |
| レビュー | 実装とは別の強いモデル。実装の文脈を共有しない | なし |

- 助言役は、各自の設定（`/advisor`）で選ぶ。リポジトリには置かない。
- 助言役は、相談のたびに会話の全体を読み直す。長いセッションほど 1 回が高くなるので、1 Issue を 1 セッションで終える。
- 軽いモデルが判断を埋めない。判断が要ったら、上の「止まる条件」で止まる。
- 実装を一段軽いモデルに渡すときは、サブエージェント `implementer`（`.claude/agents/implementer.md`。既定は `opus`。内容が軽いか、達成することとやることが明瞭な Issue なら、呼び出しで `sonnet` を指定してよい）を使える。実装と文脈を共有しないレビューは、`reviewer`（`.claude/agents/reviewer.md`。読む道具だけを持つ）に、差分と Issue を渡して頼める。

## 1 スライスの進め方

1. `ready` の Issue を、上の「次の Issue の選び方」で 1 つ選ぶ。受け入れ条件が曖昧なら、実装せずに Issue で質問する。
2. テストを先に書く（または同じコミットで書く）。書き方は下の「テストの書き方」。
3. 実装する。既存のファイルは全体の書き換えではなく差分で直す。
4. `make check` を通す。lint を無効にしたり、テストをスキップしたりして通さない。
5. 影響する文書を直す（`docs/dev/docs-hygiene.md` の自己点検）。設計判断をしたら ADR を足す。
6. PR を開く前に自己レビューをして、要約を PR の「レビューの見どころ」に書く。

## テストの書き方

| 層 | 手段 | 例 |
| --- | --- | --- |
| エンジン（`backend/internal/` のまとまり） | テーブル駆動の単体テスト。既知の理論の事実をデータとして並べ、出どころをコメントに書く。不変量には性質によるテスト | C major のダイアトニックの三和音、移調して戻すと元に戻る |
| `backend/internal/httpapi` | `httptest` のレコーダーで、JSON の形とステータスを確かめる | 存在しないパスが problem の文書を返す |
| `backend/internal/config` | テーブル駆動。環境変数を読む関数を差し替える | 範囲の外の `PORT` がエラーになる |
| 画面のロジック（hook、純粋な関数） | Vitest。DOM なしで書けるものは DOM なしで | API の応答を境界で検証する関数 |
| 画面の UI | Testing Library。role と文で確かめる。スナップショットは使わない | サーバーが答えると、版が状態の行に出る |

判断に迷ったら、プラクティスの索引（`.claude/skills/practices/index.md`）の 1 節を引く。

## 完了の定義

- 受け入れ条件をすべて満たしている。
- `make check` が通り、CI の `required (make check)` が緑。
- 振る舞いの変更にテストがある。
- 言及が変わる文書を直してある。
- 説明の文の型や、カタログの文を足した・変えたなら、`docs/architecture/explanations.md` の基準と誤りの表に照らしてある。
- PR に、スコープ外にしたことが書いてある。

## コミットと PR

- Conventional Commits。1 PR = 1 Issue = 1 スライス。
- PR 本文は `.github/pull_request_template.md` に従う。
- `main` に直接 push しない。`git push --force` をしない。

## マージ（ADR-0014）

エージェントが自分で開いた PR は、次のすべてを満たせば、エージェントがマージしてよい。

- CI の必須のチェック（`required (make check)`）が緑。
- 新しい判断を含まない。ADR、Issue のコメントの所有者の判断、`docs/` の規則で決まっていることを形にするだけ。
- 下の「所有者の OK を待つもの」に当たらない。

所有者の OK を待つもの:

- ADR を足す・変える。所有者の判断を新しく要する。
- 検査、CI、依存、ビルドとコンテナ、API の契約（`docs/api/openapi.yaml`）を変える。
- 音楽理論の立場（`docs/architecture/theory-conventions.md`）や、説明の文の規則（`docs/architecture/explanations.md`）を変える。
- 別のセッションや人が開いた PR。
- PR の大きさの予算が警告を出す（`make pr-size`。`docs/dev/harness.md`）。
- 当たるかどうか迷う。

エージェントがマージしたら、PR に、エージェントがマージしたことと、上の条件に当たる理由を 1 行で書く。
