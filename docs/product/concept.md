# コンセプトと要求整理

グラフィカルな作曲・コード進行学習アプリ chord-rambler のコンセプト。未決定事項（8 章）を決めたら、ADR に記録してこの文書を直す。

## 1. プロダクトの目的

音楽的なイメージを出発点に、ユーザーがコード進行を視覚的に探索・構築し、再生しながら学べる作曲支援アプリケーションを作る。

最も大切にするのは、**ユーザー自身がコードやその組み合わせを採用し、各選択の意味・役割を理解しながら組み上げる体験**である。完成したコード進行をAIが生成することも許容するが、それだけが体験の中心ではない。Scratchと共通するのは「視覚的な操作によって構造を組み立て、試す」思想であり、画面をScratchに似せる意図はない。

対象として、作曲や音楽理論、特にコード進行を学びながら創作したい初心者を想定する。説明には教育上の単純化を許容するが、音楽的な意味に明白な誤りや矛盾を含めない。

## 2. 体験の基本原則

1. **選んで学ぶ**：コードや展開を一意の正解として押しつけず、異なる意図を持つ候補から選び、理由を確かめる。
2. **視覚と聴覚を行き来する**：ノード・小節・度数・機能を見て操作し、すぐに再生して検証する。
3. **全体の意図と局所の手段を区別する**：「浮遊感」「切なさ」などは表現したい意図であり、sus2、maj7、ペダルポイントなどは実現手段の候補である。一対一対応させない。
4. **全体からも局所からも作れる**：グラフ型（局所から全体へ）と計画型（全体から局所へ）の両方の体験を持つ。
5. **AI支援とユーザーの主導権を両立する**：AIによる構造化、候補提案、説明、一括生成を使えるが、採用・変更・比較の余地を維持する。

## 3. 扱う情報の文脈と階層

### 3.1 表現意図（ユーザーが「どう聴かせたいか」）

自然言語や複数のキーワードで、情景・感情・印象・作品の参照などを指定する。例：夜、雨、明るい、切ない、浮遊感、重厚さ、BGM、特定の楽曲やアーティストに関する参照。複数のワードの強さ・比率を指定する形式も検討対象。

### 3.2 全体の音楽的文脈（マクロ設定）

- 音楽ジャンル・文化的スタイル：J-POP、スウィング・ジャズ、ケルト音楽、ワルツ等
- 基準となるキー、スケール、モード：C Major、マイナー、ミクソリディアン等
- 全体で採用したい和声技法・コード進行パターン：枯葉進行、ドミナント・ペダル等
- 演奏スタイル：コード、アルペジオ、ベース・ドラムのパターン等
- 音色・サウンドデザイン：チップチューン風の音色等
- BPM、拍子、想定小節数・区間構成等

これらは同じ種類の属性ではない。例えば「ケルト風」は、音階だけでなく旋律やリズム、音色など複数の要素に影響しうる。自然言語を構造化するときは関係する要素へ展開し、ユーザーによる確認・修正を可能にする。

### 3.3 局所の音楽的意図と操作（ミクロ設定）

特定コードへのテンション追加、sus2/sus4への変更、借用和音、転調、特定区間への浮遊感・緊張感・解決感の追加などを扱う。進行の前後関係と楽曲全体の文脈を踏まえて提案・解釈する。

### 3.4 コードの実体と音楽的な解釈

コードノードは、少なくとも**コード名**（例：Am7、Cmaj7）と、文脈に基づく**度数表記**（例：vi7、Imaj7）を表示できる。必要に応じてトニック、サブドミナント、ドミナントの機能、採用意図、前後のコードとの関係を説明する。

度数や機能はコード自体の不変な属性ではなく、基準キーや局所的な調性・モード等に依存する。借用和音、セカンダリー・ドミナント、転調を含む進行で、表示の解釈を一つに固定しない設計を検討する。

基準キーを全体設定に持たせ、コード間の音程関係を保った**移調**を可能にする。コード名はキーに合わせて変わり、度数表記は適切な基準に対して読み直す。

## 4. 2つの主要な作曲体験

### A：グラフ型 — 次のコードを探索して接続する

コードをノードとして左から右へ接続し、一つの進行を成長させる。現在の末尾に対して、次のコード候補を複数提示し、各候補の度数、機能、音楽的な意味、期待される印象、次の展開を説明する。ユーザーは候補を比較・試聴・採用し、必要ならコードを変形する。

主な学習対象は、**コード間のつながり・緊張と解決・局所的な和声の選択**。候補の分岐は提案のためであり、確定した進行は基本的に一本の順序として再生する。

### B：計画型 — 小節の役割を決めて埋める

先に小節数や区間構成を決め、各小節・区間に「導入」「提示」「浮遊」「緊張」「解決」「余韻」などの役割やニュアンスを指定する。AIによる全体構成の提案も許容する。各位置に、前後関係と全体の計画に適合するコード候補を提示し、ユーザーが選んで埋めていく。

主な学習対象は、**構成・展開の設計・区間の役割を実現する和声の選択**。小節ごとのコード数や演奏タイミングは後から調整できる。

両方式は相互排他的ではなく、同じ音楽モデルの異なる操作ビューとなる可能性がある。ただし、画面を統合するかモードを分けるかは未決定。

## 5. 時間配置・演奏・試聴

**和声の順序**（コードの接続）、**時間的配置**（何小節目の何拍から何拍まで鳴るか）、**演奏表現**（コード／アルペジオ／音色／リズム／ベース・ドラム等）を概念として分ける。

基本は1コード1小節とするが、1小節内の複数コード、裏拍からの開始、持続時間の変更もできる。作成した進行は再生でき、採用する前後の候補や変更案を比較できることが望ましい。演奏・編曲については初期値や定型パターンを提供し、作曲の中心体験を妨げないようにする。

## 6. AIおよび定義済みパターンによる支援

- 曖昧な自然言語のイメージを読み取り、音楽的な文脈・パラメータの**編集可能な候補**に変換する。
- 次のコード、指定小節のコード、部分的な変更、曲全体の展開を複数提案する。
- 「なぜその候補なのか」を**音楽理論上の説明**と**期待する印象・効果**に区別して説明する。
- ルールや事前定義されたコード進行・演奏パターンのカタログも使える。すべてを生成AIに依存させない。
- 完成した進行の一括生成も許容する。ただし生成結果をノード・度数・小節・説明へ展開し、ユーザーが再編集・比較・試聴できることを重視する。

## 7. 想定する共通の利用フロー

1. イメージを自然言語または項目で入力する。
2. AIと定義済みルールが音楽的文脈を提案し、ユーザーが確認・調整する。
3. グラフ型または計画型でコード進行を組み立てる。必要ならAIの完成案から編集を開始する。
4. 度数・機能・採用理由を確かめつつ、部分的な和声の変化を加える。
5. コードを小節・拍に配置し、演奏スタイルを適用する。
6. 再生・比較し、コード・構成・キー・演奏設定へ戻って試行錯誤する。

この順序はガイドであり、不可逆なウィザードではない。

## 8. 重点的な未決定事項

1. **概念モデル**：表現意図、音楽的文脈、和声技法、演奏表現の関係と変換ルール。
2. **和声データモデル**：コード実体、度数、機能、参照調性、転調・借用和音等の分離と整合性。
3. **AIとルールの責務分担**：候補生成・制約・説明・カタログの境界と提案品質の検証方法。
4. **2つの体験の関係**：別モードか共通キャンバスか、双方向の切替や同じ進行の共有方法。
5. **時間配置と構成の対応**：グラフの順序、小節の役割、拍単位の演奏イベントの関係。
6. **初心者向け説明の粒度**：理論上の複数解釈をどこまで表示し、どこを単純化するか。
7. **音色・伴奏の編集範囲**：コード進行学習が主役であることを損なわない機能の優先順位。
